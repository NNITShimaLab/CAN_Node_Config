# CANとシリアルの通信仕様

この文書は現行スケッチが送受信するデータを定義します。CANはClassic CAN、250kbps、データ長8バイトです。通常データに11ビットの標準ID、管理通知に29ビットの拡張IDを使用します。

## CAN.write()で送信するもの

| 種類 | ID | 送信条件・周期 |
|---|---|---|
| 管理通知 | 拡張ID 0x10000000～0x17FFFFFFの一部 | CAN初期化成功後、未設定・探索・設定済み・エラーの各状態で継続 |
| テストデータ | 割り当てた標準ID 0x100～0x10F | 設定済み、保存処理完了、起動後3秒以上の条件で約1秒ごと |

管理通知とテストデータは別のメッセージです。相手がフレームを受信してACKを返すことと、相手のスケッチが内容を処理することも別です。

### 管理通知の拡張ID

```text
extended_id = 0x10000000 | (tag << 2) | part
```

| ビット位置 | 内容 |
|---|---|
| 28～27 | 管理通信用の固定値：10（二進数） |
| 26～2 | tag：固有IDから生成した25ビットの値 |
| 1～0 | part：固有IDの分割番号。0、1、2のいずれか |

tagは16バイトのUIDへFNV-1aを適用して求めます。演算は32ビット符号なし整数で行い、乗算のオーバーフローは下位32ビットを残します。

```text
hash = 2166136261
各UIDバイトについて:
    hash = (hash XOR byte) × 16777619
    hash = hash AND 0xFFFFFFFF
tag = hash AND 0x01FFFFFF
```

UIDのバイト列はR_BSP_UniqueIdGet()が返す4ワードを順に並べ、各ワードの上位バイトから格納します。この順序で16バイトを16進表記すると、ログの32桁UIDになります。

### 管理通知の8バイト

| バイト位置 | 内容 |
|---|---|
| 0 | 上位4ビット＝形式バージョン1、下位4ビット＝state |
| 1 | 通信IDから0x100を引いた番号。未設定・候補なしは0xFF |
| 2～7 | UIDの断片。partに対応する最大6バイト |

| part | バイト2～7へ格納する内容 |
|---:|---|
| 0 | UIDのバイト0～5 |
| 1 | UIDのバイト6～11 |
| 2 | UIDのバイト12～15、続いて00、00 |

stateは0=未設定、1=探索、2=候補確認、3=設定済み、4=エラーです。例えばstate=3なら、バイト0は0x13になります。エラー番号そのものは管理フレームへ入れていません。

1フレームの送信間隔は`75 + tag % 31`msで、75～105msです。partは0→1→2→0の順に進むため、通常は225～315msで1組を送ります。CAN.write()が失敗した場合はpartを進めず、次の周期で同じ断片を再試行します。

### テストデータの8バイト

| バイト位置 | 内容 | 表記 |
|---|---|---|
| 0 | 識別マーカー前半 | CA |
| 1 | 識別マーカー後半 | FE |
| 2 | 通信ID − 0x100 | 00～0F |
| 3 | テストデータ形式バージョン | 01 |
| 4～7 | 32ビット送信連番 | リトルエンディアン |

0x101の機器が連番1を送る例:

```text
フレーム種別: 標準ID
CAN ID:       0x101
データ長:     8
データ:       CA FE 01 01 01 00 00 00
```

送信連番は起動時0です。送信を試みるたびに1増え、失敗した場合も増えます。ID解除ではリセットせず、MCUの再起動で0へ戻ります。32ビットの上限に達すると0へ戻ります。

## CAN.read()で読み取った後の処理

CAN.read()でCAN ID、フレーム種別、データ長、データを取り出します。処理は次の順です。

1. 標準IDのフレームなら、長さやデータ内容にかかわらず、範囲内のIDを使用中として記録します。自分の設定IDと一致した場合は重複判定にも使います。
2. 長さが8バイトでなければ、以降の処理を行いません。
3. 拡張IDなら管理通知として検査・復元します。
4. 標準IDならテストデータの受信条件を確認し、一致すればrxを増やします。

### 管理通知の検査

管理範囲の拡張ID、part=0～2、形式バージョン1、state=0～4、ID番号の範囲を確認します。設定済み・候補確認中なのにID番号が0xFFの場合は無視します。

相手ごとに3つの断片を集めます。組立中にstate・IDが変わった場合や、1秒を超えた場合は断片の収集をやり直します。3つそろったら復元UIDのハッシュがtagと一致するか確認します。自分と同じUIDの通知は相手として登録しません。

復元した相手UID、状態、ID、受信時刻を管理テーブルへ格納します。これを空きID選択、候補の優先順位、設定済みIDの重複検出に使用します。相手の管理テーブルは16件です。

### テストデータをrxへ数える条件

次の全条件が成立したときだけ、累積受信数rxを1増やします。

- 標準IDが0x100～0x10F。
- データ長が8バイト。
- バイト0と1がCA FE。
- バイト2が`受信CAN ID − 0x100`と一致。

現行実装はバイト3のバージョンを検査せず、バイト4～7の送信連番も解析しません。そのためrxは「条件に合うフレーム数」であり、連番の欠落・重複・順序や、相手ごとの受信数を表す値ではありません。管理通知はrxに含みません。

## シリアルは約1秒ごとに1行出力する

Serial.begin(115200)で初期化します。USBシリアルが接続されていなくても、CANとボタン処理は進みます。Serialが利用可能な場合だけ、約1秒ごとに状態を出力します。

形式は空白区切りの`項目=値`です。項目の順序は固定で、行末はSerial.println()によるCRLFです。

```text
UID=<32桁16進数> state=<10進数> ID=0x<16進数> error=<10進数> rx=<10進数> tx_failed=<10進数> TEC=<10進数> REC=<10進数>
```

説明用の架空UIDを使った出力例:

```text
UID=00112233445566778899AABBCCDDEEFF state=3 ID=0x101 error=0 rx=42 tx_failed=0 TEC=0 REC=0
```

| 項目 | 定義 |
|---|---|
| UID | 自分のRA4M1ハードウェア固有ID。32桁、大文字16進数、0xなし |
| state | 0=未設定、1=探索、2=候補確認、3=設定済み、4=エラー |
| ID | 自分の通信ID。0x付き大文字16進数、桁数固定なし。未設定は0xFFFF |
| error | 検出したアプリケーションエラー番号。0～6の意味は動作仕様を参照 |
| rx | 条件に合った通常テストデータの累積受信数 |
| tx_failed | 通常テストデータのCAN.write()が負値を返した累積回数 |
| TEC | R_CAN0->TECRから読み出した送信エラーカウンター |
| REC | R_CAN0->RECRから読み出した受信エラーカウンター |

rxとtx_failedは32ビット符号なし整数です。起動時0、ID解除では維持、再起動で0に戻ります。管理通知の送信失敗回数はtx_failedへ含めていません。

TECとRECはCANコントローラーが更新する値で、累積件数ではありません。正常通信によって減る場合があります。CAN初期化失敗時は、このスケッチがTECとRECを0として出力するため、errorと合わせて判断してください。各レジスターは順番に読み出しており、厳密な同時スナップショットではありません。

CAN.write()の成功は送信要求が受け付けられたことを示します。tx_failedが増えないことだけでは相手のアプリケーション受信を保証できません。双方のrxの増加、TEC/REC、state/errorを合わせて確認してください。

## 現在出力していないもの

受信フレームそのもの、相手のUID一覧、相手の連番、管理通知の送信失敗回数、CAN.write()の戻り値そのものは出力していません。表示中のUIDとIDは、常に自分の値です。
